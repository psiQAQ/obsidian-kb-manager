# 接管、迁移和恢复知识库

## 整库迁移与身份冲突

- **复制或移动整库**。保留根目录的 `kb.toml`。在目标 Vault 导入这个文件，核对 ID、首页、位置、偏好和受管文件预览，再登记。用户改写过的绑定保留并提示复核。只从 Git 克隆时，可以补选原清单恢复原身份，也可以明确选择按新库接管。
- **找回登记**。登记表丢失时选择目录扫描，核对候选库后重建。原路径失效时，选择清单重新定位；同一 Vault 中的独立副本需要分配新 ID。重复身份解决前，相关库暂停写入。

## 文件和设置存放位置

| 文件或位置 | 内容 |
|---|---|
| 库根 `kb.toml` | 目录映射、身份、首页、模板、受管文件指纹，以及明确保存的逐库偏好。新库通过 `/kb.toml` 默认忽略它。整目录复制时请一并带走。 |
| 插件 `data.json` | `registeredLibraries` 保存已登记库的 Vault 相对路径，`language` 和 `defaults` 保存语言和全局 Git 默认值。文件位于当前 Vault 配置目录的 `plugins/knowledge-base-manager/` 下。 |
| Obsidian 设备本地存储 | 建库父目录、自定义模板目录、自动操作授权和未完成操作的恢复信息。在新设备上重新确认自动操作。 |
| 库内 `.git/config`、系统 Git、SecretStorage | 库级 Git 身份与远端由 Git 管理，认证由系统或选定的 SecretStorage 凭据提供。 |

从 2.0 升级后，可在全局设置中核对旧版逐库偏好。确认库 ID、目标清单和值，再将选定库的覆盖写入 `kb.toml`。旧授权需在本设备核对后恢复。

### 迁移旧登记表

1. 如果 Vault 根仍有 `.kb-manager/libraries.json`，桌面端会在加载后显示迁移预览。也可以从侧栏 **登记 → 预览旧版登记迁移** 重新打开。核对旧路径数、目标文件和合并后的路径列表。选择 **稍后处理** 可继续查看已有登记，创建或更改登记前需先完成迁移。
2. 若 Vault 根由 Git 管理，核对预览中的忽略规则。默认目标是 `/.obsidian/plugins/knowledge-base-manager/data.json`，自定义配置目录使用其实际位置。旧的 `/.kb-manager/` 规则只覆盖原位置。Git 会继续跟踪已纳入版本控制的文件，公开提交前应检查 `git ls-files -- <data.json 的相对路径>`；有输出表示仍在跟踪。
3. 选择 **确认迁移**。插件保留目标中已有的登记，按路径合并、保存并回读核对，再删除旧文件。旧目录中还有其他文件时会保留目录。磁盘写入或回读失败时，重新打开登记预览即可复核后重试。登记路径在预览后改变时，需重新核对。

每个 Vault 配置目录有自己的插件数据。若两套配置以前共用根登记表，确认迁移前请记下另一套配置所需的路径，之后可在该配置中扫描并重新登记。迁移只处理路径列表，各知识库的 `kb.toml`、笔记和 Git 历史均沿用原内容。

## 归档、目录改名和中断恢复

- **编辑和归档**。打开行菜单 **… → 编辑** 可调整显示名、简介或归档状态。确认界面列出清单修改。归档后仍可打开并查看历史，在编辑界面恢复活动状态。
- **目录移动或改名**。先在 Vault 中建立目标父目录，再选择库的 **移动**。可在预览时登记已有的新父目录。同父目录更改目录名即可改名。检查预览中的源、目标、受管字段和已解析链接。移动使用同一文件系统内的目录改名。旧路径的库外链接、剪藏目标和自定义查询可能需要手动更新。
- **中断恢复**。移动中断后，管理器显示已记录的操作。选择 **复核并继续**。若 ID、Git 索引、HEAD 或受管文件内容变化，先检查提示涉及的文件，保留自己的编辑。

## 给旧库启用专项检验

旧库可直接运行通用检验。对于 2.4.0 及更早版本创建的融合 LLM Wiki 或 Kepano，打开 **… → 预览清单升级**，展开 `checks/` 下的脚本和 `kb-template.json` 查看内容与 SHA-256，再选择 **应用清单升级**。升级保留原库 ID 和偏好，并将 `.log/` 加入本库 Git 忽略规则。若同名脚本或声明已有个人改动，预览会列出需要人工核对的文件。

可先运行通用项核对现状，检查结果及日志位置见[运行知识库检验](diagnostics.md)。
