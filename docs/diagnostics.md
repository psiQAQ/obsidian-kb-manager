# 运行和解读知识库检验

在桌面管理器打开目标库的 **… → 检验**。在 **运行检验** 页直接运行常规与模板专项。如果准备移动或克隆这个库，将检查范围切为 **自选检查项**，勾选 **可移植性** 后运行。历史记录和离线工具分别在 **历史报告**、**检验工具** 页。

| 想确认的事情 | 选择与结果 |
|---|---|
| 笔记、附件和清单能否正常使用 | 通用项检查清单与登记、属性语法、链接与嵌入、标题与块、Canvas、Bases 和受管绑定。报告按严重程度给出规则编号、文件和可用的位置。 |
| 单独搬走这个库会缺什么 | 可移植性列出已解析的跨库依赖。Canvas 的文件节点、分组背景、文本链接也在范围内；同名候选与实际目标分别标明。 |
| 内容是否符合所选模板的组织方式 | 选择模板声明的专项。比如新版知识花园会对拟分享笔记指向私有页面的链接发出警告。桌面使用 Obsidian 实际选中的目标。 |

桌面默认在本库和已登记库中查找同名候选。勾选 **在整个 Vault 查找同名候选** 可纳入其他文件夹，两种范围都会显示 Obsidian 实际解析到的目标。

只选 **清单与登记** 时，检验清单声明的路径是否存在，不打开 Markdown 正文。离线单独检查 **Canvas** 时，需要核对本库 Markdown 标题或块的节点才会读取对应笔记。

**自己新建的笔记**用「链接与嵌入」检查。比如一篇作业里的 `[[../课程索引]]` 会从这篇作业所在的目录找目标。即使笔记中有一段文字恰好等于库根路径，也不会因此进入受管清单。普通链接可以合法指向其他库，想知道整库搬走会影响哪些链接时，再选「可移植性」。

**受管绑定**用来核对模板明确声明、随库改名或移动需要更新的位置。例如，两个课程库都有一份可打开的课程总览，但库甲首页声明的总览应指向库甲，Base 的课程筛选也应限定库甲。检查会比对清单指纹；文件经过编辑后，可从本库 Git 历史中查找与原指纹相符的版本，核对相应链接或筛选字段。只在首页末尾加字、或 Obsidian 保存 Base 时改变 YAML 引号和键序，只要仍能核实绑定，就不会产生绑定警告。缺少足够证据时，查看报告中该项的未验证原因。移动或修复仍会单独核对文件内容，经过编辑的文件留给用户确认。

同时看**严重程度**和**覆盖情况**。例如，图片引用已确认跨库，另一篇 Markdown 又无法读取，同一份报告会同时显示警告和「部分完成」。在 **各项检查范围** 查看原因，再按严重程度查看问题、文件位置和规则。离线短链缺乏 Vault 索引时也可能显示未验证。

运行中选择 **取消检验**，面板会等待正在运行的检查进程退出，再显示已完成的结果和未运行的检查项。关闭检验窗口或停用插件也会停止本次检查。取消的报告只在当前检验窗口查看，历史记录只收录已保存的报告。

选择 **查看报告 JSON** 可打开原始报告。选中所需文本或点击 **全选** 后，使用系统复制命令。

## 核对历史报告

在 **历史报告** 中打开一份结果。**规则与输入版本** 显示检验引擎、规则文件和摘要，以及本次读取的库内文件和目录的版本。日志以相对路径记录参与核对的项目，输入版本根据文件状态和目录条目计算。打开报告时会核对这些输入。若继续修改文件，可选 **核对当前文件** 重新核对，无需重新读取正文。单选清单与登记时，笔记正文的修改不会使报告过期，路径的增删或移动会使报告过期。核对范围不包含宿主链接缓存、登记表及脚本自行访问的外部数据。旧报告仍可打开，界面会说明其输入版本无法核实。

打开较新的报告后，可在 **与早先报告比较** 选择基准。比如修复一处损坏的链接后，重新运行相同的检查，再选择修复前的报告查看 **已解决**。**新增** 和 **仍存在** 也会列出文件位置。比较使用检查项、问题编号、文件和证据来匹配问题，行号移动不产生新的问题。界面会标出规则版本变化，以及因检查范围、运行环境或不完整覆盖而缺少可比结果的检查项。

## 审查库内规则与更新工具

新实例的 `checks/common/` 保存可编辑的通用规则。以属性检验为例，`checks/common/properties.mjs` 的路径和 SHA-256 与当前插件或独立工具随版记录一致时，运行该版本内置的规则。桌面执行这类通用规则无需安装独立 Node.js。编辑文件后，选择 **审查脚本** 比较源码、核对 SHA-256 并授权这份内容，再用本机 Node.js 运行。再次编辑会产生新的摘要。离线端使用 `--trust-digest` 传入已审阅的摘要。直接从命令行启动 `checks/kb-check.cjs` 时，须先信任入口文件本身。

已带工具的实例可以在检验界面比较已安装版本与插件分发版本，再确认更新。预览会标出已修改的文件，供手动合并。日常运行与插件升级都会保留这些修改。

新版桌面插件及其导出的离线入口能识别旧版官方受管绑定脚本，并运行新版的路径核对逻辑。这种情况下，报告的 `rule.sourceDigest` 记录库内旧文件的摘要，`rule.digest` 记录实际执行规则的摘要。直接运行实例中原有的旧 `checks/kb-check.cjs` 会使用旧逻辑；如需离线也按新版核对，可在 **检验工具 → 查看版本与差异** 检查待更新文件。

## 专项脚本与日志

模板专项通过本机 Node.js 运行，脚本拥有当前系统账号的文件和网络权限。内置脚本按发行包中的摘要识别；个人脚本通过检查项旁的 **审查脚本** 查看源码和 SHA-256，再选择 **授权此版本**。脚本内容改变后需重新核对。请只运行你信任的脚本。

通用检验读取清单、笔记、附件引用及宿主提供的元数据，保留笔记内容、Git 暂存区和提交历史。新建实例会在默认由 Git 忽略的 `.log/` 保存每次检验的 JSON 报告；受管路径的修复在独立的预览中确认。模板专项须遵循只读约定。离线 agent 可调用 `kb-check.cjs` 并读取报告的 `status`、各项 `coverage` 和 `diagnostics`。[专项脚本协议](template-authoring.md)

## 离线运行与读取报告

3.2.0 起，新建库的首次提交包含 `checks/kb-check.cjs` 和 `checks/common/` 下的通用规则。进入实例根目录，在装有 Node.js 的机器上运行：

```sh
node ./checks/kb-check.cjs --library . --list
node ./checks/kb-check.cjs --library . --checks all
```

需要指定宿主 Vault 时加上 `--vault-root "<Vault 路径>"`。可移植性可单独用 `--checks portability` 检查。旧库继续使用原有检验方式，可从 **… → 检验 → 检验工具 → 选择保存位置** 导出独立入口。新版入口的 JSON 增加可选的 `engineVersion`、`inputVersion` 和各检查项的 `rule` 字段，原有参数、退出码和 `--history` 用法保持兼容。

CLI 将报告作为单行 JSON 写到标准输出。若两库都有 `[[实验记录]]`，桌面可以查询 Obsidian 在当前来源页选中的目标；单选可移植性可查看同名候选。离线只有短链时，保留报告中的未验证原因。agent 即使收到退出码 0 也应读取报告，例如将上条命令的输出保存为 `report.json` 后运行：

```sh
node -e "const r=JSON.parse(require('node:fs').readFileSync('report.json','utf8')); console.log(r.status); for (const c of r.checks || []) console.log(c.id,c.status,c.coverage,c.diagnostics)"
```

退出码 1 表示报告含错误级诊断，2 表示运行或日志失败、脚本尚未授信，或参数无效。个人脚本可在核对实际文件后用 `--trust-digest` 指定认可的摘要；自定义 Vault 配置目录用 `--config-dir` 指定目录名。

运行检查、列出专项（`--list`）和读取历史（`--history`）都使用指定的 Vault 范围。若列出专项或读取历史时收到退出码 2，先核对 `--library` 是否位于 `--vault-root` 内，以及路径是否误指向 Vault 配置目录。

## 复测选择性读取

在已备齐项目依赖的仓库根目录，以 Node.js 24 运行以下命令。脚本在仓库 `.tmp/` 生成并清理合成样本。目标库有 100 篇各 8,199 字节的 Markdown，另有 0、10 或 100 个登记库。每组预热一次，随后记录五次运行中位数、目录读取和成功发起的文件读取次数。耗时包含日志保存和当时套件的 Node 启动时间，不包含 Obsidian 界面。

```sh
node scripts/prepare-test-kit.mjs
node --import ./tests/fixtures/check-kit-env.mjs --experimental-strip-types scripts/benchmark-diagnostics.mjs
```

Windows / Node.js 24.19.0 下，单选清单与登记的每次读取结果如下。三个时间依次对应 0、10、100 个其他登记库。优化前为 `a02b293`，在相同检出中使用相同基准脚本测得。

| 目标库 | 目录读取 | 文件读取 | Markdown 读取 | 中位耗时，毫秒 |
|---|---:|---:|---:|---|
| 旧库 | 2 → 2 | 101 → 1 | 100 → 0 | 82.23 → 2.39 / 88.96 → 2.11 / 86.93 → 2.45 |
| 已装通用规则 | 2 → 2 | 102 → 2 | 100 → 0 | 123.96 → 42.79 / 146.72 → 43.92 / 144.35 → 42.44 |

同时选清单与登记及属性语法，各规模仍读取 100 篇 Markdown。旧库总共读取 101 个文件，已装通用规则的库读取 103 个文件。

应用随版规则执行与输入版本记录后，已装通用规则的库仍读取 2 个文件和 0 篇 Markdown。相同三个规模下，单选清单与登记的中位耗时分别为 3.19、2.85、3.06 毫秒。
